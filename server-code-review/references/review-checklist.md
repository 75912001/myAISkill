# 通用审查清单

## Finding 质量标准

只报告有具体失败模式的可行动问题。每条 finding 必须回答：

- 会出什么问题？
- 相关代码在哪里？
- 为什么会发生？
- 对用户或运行环境有什么影响？
- 哪个修改能修复或降低风险？

避免只基于偏好、风格或猜测架构方向的 finding。

## 核心检查

- 正确性：错误假设、边界错误、nil 解引用、分支条件错误、陈旧状态。
- 回归风险：行为变化缺少迁移、兼容处理或调用方更新。
- 错误处理：吞掉错误、状态码错误、错误映射误导、缺少上下文。
- 数据安全：写丢失、非幂等重试、部分写入、缺少事务/pipeline 语义。
- 并发：数据竞争、actor 顺序假设、死锁、goroutine 泄漏、timer 生命周期问题。
- 资源生命周期：连接、stream、文件、Redis client、etcd lease、后台 worker 未关闭。
- 配置：默认值不匹配、单位错误、环境相关地址错误、缺少校验。
- 可观测性：失败路径缺少日志、日志噪音过多、日志缺少关键标识。
- 测试：缺少变更行为、失败路径、并发、配置解析和集成边界覆盖。

## 审查方法

- 从变更代码向调用方和被调用方扩展阅读。
- 对比 proto/API/config 契约和实现。
- 涉及生成文件时，检查生成文件是否匹配源定义。
- 优先报告小而可验证的问题，不做宽泛结论。
- 只有发现具体 bug 类别或行为风险时，才提出测试缺口。
