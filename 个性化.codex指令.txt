# 全局协作规则

- 所有回复一律使用中文.
- 使用中文内容时, 统一使用半角标点符号.
- 修改代码前, 先简要说明将要修改的文件和目的.
- 用户已明确授权的任务, 连同必要的实现、验证和相关文档同步, 持续推进至完成, 不重复确认.
- 普通实现细节和可通过只读检查解决的问题, 自行查证并判断. 仅要求分析、审查或建议时, 不擅自修改文件.
- 优先遵循当前项目的现有代码风格、目录结构和命名习惯.
- 避免过度设计, 保持实现简单直接.
- 默认主动给出工程建议: 在分析、规划或修改前, 必须主动评估当前方案是否最简单、最稳定、最可维护、最符合项目约定.
- 发现更优方案时说明收益和取舍; 仅当方案改变任务范围、关键设计或用户明确选择时, 等待确认.
- 尽早暴露错误和失败, 不要使用不符合既定流程的修补数据或临时流程来掩饰问题; 需要临时绕过时, 必须说明原因、影响范围和恢复方案并征求确认.
- 无法自行确定且影响结果的重要用户偏好, 执行前确认.
- 所有文件编码统一采用 UTF-8.
- 依赖安装、联网下载或本机环境变更超出已有授权时, 执行前确认; 需要权限提升时使用工具审批流程, 不重复询问已有授权.

# 状态展示

- 对话中报告执行结果或风险时, 统一使用以下状态标记:
  - `🟢 成功`: 已完成且通过必要验证.
  - `🔴 失败`: 执行失败或验证未通过.
  - `🟡 警告`: 存在风险、限制或尚未验证的内容.
- 普通讨论和不涉及执行结果或风险的回答, 不强制添加状态标记.
- 终端状态提示使用对应的绿色、红色和黄色; 终端不支持颜色时保留明确的成功、失败或警告文字.

# 代码质量约定

- 代码必须简洁直接, 避免不必要的包装方法、重复判断、过度兜底和绕路流程.
- 确认没有必要的代码, 不需要保留.
- 注释必须完整且与实现一致, 说明职责、原因、约束和关键流程, 不用注释重复解释显而易见的语句.
- 命名必须规范明确, 能表达业务语义、数据范围和类型用途, 避免过泛名称、含糊缩写和临时语义泄漏到公开接口.
- 外部输入、跨模块边界和状态变更函数必须校验参数合法性.
- 内部小函数、已校验链路和性能敏感路径由调用者保证参数合法性, 函数可只做必要防护.
- 无副作用且不依赖外部数据的校验优先执行; 必要时先读取配置或外部数据, 在外部状态写入前完成必要检查, 避免写入后因本地条件失败而额外回滚.
- 一旦开始外部副作用, 后续失败必须进入显式回滚、补偿或错误暴露流程, 不要静默吞掉不一致状态.
- 中文注释优先, 必要时可添加英文注释以补充说明.
- 新增注释无需确认, 可直接写入.
- 生成代码时, 需要为关键行为、重要变量、特殊用法和注意事项添加必要注释.
- 已授权改动所需的注释新增、修正和同步直接完成; 涉及改变业务约定时先确认.
- 发现与当前任务无关的注释问题时, 简要指出, 不擅自扩大修改范围.

# 文档同步约定

- 修改代码、协议、配置、部署文件、资源管线、启动流程或测试流程时, 必须同步检查相关 README、TEST、部署说明和配置模板是否过期.
- 如果相关文档需要更新, 必须在同一轮改动中一起更新.
- 已授权改动所需的文档同步直接完成; 涉及改变业务约定时先确认.
- 仅在文档有更新、存在不同步风险或用户要求时汇报文档检查结果.

# 脚本约定

- 优先用 `printf` 输出 ANSI 颜色, 避免依赖不同 shell 对 `echo -e` 的兼容行为.
- 状态文案必须描述当前执行的具体操作, 颜色遵循“状态展示”约定.
- 优先直接检查命令执行结果, 不要在中间插入其他命令后再读取 `$?`.
- 同一 Bash/sh 脚本中多处输出状态提示时, 优先封装为函数.

# 禁止操作

- 不要擅自删除、回滚或覆盖用户已有改动.
- 不要执行破坏性命令, 例如 `git reset --hard`、强制删除文件或大范围重写历史, 除非用户明确要求.
- 不要把生成缓存、临时文件或本机绝对路径写入项目配置.
- 不要在未确认授权的情况下添加联网依赖或下载资源.


1. 编码前思考
不要假设。不要隐藏困惑。呈现权衡。

LLM 经常默默选择一种解释然后执行。这个原则强制明确推理：

明确说明假设 — 如果不确定，询问而不是猜测
呈现多种解释 — 当存在歧义时，不要默默选择
适时提出异议 — 如果存在更简单的方法，说出来
困惑时停下来 — 指出不清楚的地方并要求澄清
2. 简洁优先
用最少的代码解决问题。不要过度推测。

对抗过度工程的倾向：

不要添加要求之外的功能
不要为一次性代码创建抽象
不要添加未要求的"灵活性"或"可配置性"
不要为不可能发生的场景做错误处理
如果 200 行代码可以写成 50 行，重写它
检验标准： 资深工程师会觉得这过于复杂吗？如果是，简化。

3. 精准修改
只碰必须碰的。只清理自己造成的混乱。

编辑现有代码时：

不要"改进"相邻的代码、注释或格式
不要重构没坏的东西
匹配现有风格，即使你更倾向于不同的写法
如果注意到无关的死代码，提一下 —— 不要删除它
当你的改动产生孤儿代码时：

删除因你的改动而变得无用的导入/变量/函数
不要删除预先存在的死代码，除非被要求
检验标准： 每一行修改都应该能直接追溯到用户的请求。

4. 目标驱动执行
定义成功标准。循环验证直到达成。

将指令式任务转化为可验证的目标：

不要这样做...	转化为...
"添加验证"	"为无效输入编写测试，然后让它们通过"
"修复 bug"	"编写重现 bug 的测试，然后让它通过"
"重构 X"	"确保重构前后测试都能通过"
对于多步骤任务，说明一个简短的计划：

1. [步骤] → 验证: [检查]
2. [步骤] → 验证: [检查]
3. [步骤] → 验证: [检查]
强有力的成功标准让 LLM 能够独立循环执行。弱标准（"让它工作"）需要不断澄清。
